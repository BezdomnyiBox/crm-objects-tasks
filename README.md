# Объекты и задачи — мини-CRM для строительной компании

Руководитель (**постановщик**) создаёт объекты — стройки — и ставит по ним задачи. **Исполнители** берут задачи в работу и отправляют на проверку, постановщик принимает работу или возвращает на доработку. Каждая смена статуса попадает в историю, которую нельзя подделать.

**Стек:** React 19 + TypeScript + Vite · Mantine (интерфейс) · TanStack Query · Supabase (Postgres + Auth).
**Главная идея:** правила доступа живут **в самой базе** (RLS, функции, триггеры), а не в интерфейсе. Если обратиться к Supabase напрямую, минуя сайт, правила работают так же.

**Демо:** https://crm-objects-tasks-dusky.vercel.app (доступы выдаются проверяющим отдельно).

## Что умеет

| Роль | Возможности |
| --- | --- |
| **Постановщик** | создаёт, редактирует и удаляет объекты и задачи; назначает исполнителя; принимает задачи или возвращает на доработку (с обязательным комментарием); видит всё |
| **Исполнитель** | видит только **свои** задачи и объекты, где у него есть задачи; берёт задачу в работу и отправляет на проверку |

Постановщиков и исполнителей может быть несколько. Статусы и переходы:

```
Новая ──исполнитель──► В работе ──исполнитель──► На проверке ──постановщик──► Принята
                          ▲                           │
                          │                           └──постановщик + комментарий──► На доработке
                          └────────────исполнитель───────────────────────────────────────┘
```

Любые другие переходы запрещены — на уровне базы. Экраны: вход по email и паролю · список объектов · карточка объекта со списком задач · карточка задачи (данные, доступные кнопки, история) · «Мои задачи» (исполнитель) · «Все задачи» (постановщик, сверх ТЗ).

## Как запустить

Нужны **Node.js 22+** и бесплатный аккаунт [Supabase](https://supabase.com). Supabase CLI — по желанию.

**1. Зависимости**

```bash
npm install
```

**2. Проект Supabase.** В [панели Supabase](https://supabase.com/dashboard) создайте проект (бесплатный план подойдёт). Запомните адрес `https://<project-ref>.supabase.co`.

**3. Миграции.** Четыре файла из [`supabase/migrations`](supabase/migrations), строго по порядку имён.

```bash
supabase login
supabase link --project-ref <project-ref>
supabase db push
```

Без CLI: откройте *SQL Editor* и по очереди выполните содержимое четырёх файлов.

**4. Закройте открытую регистрацию.** В панели: *Authentication → Sign In / Providers* → выключите **Allow new users to sign up**. Либо примените [`supabase/config.toml`](supabase/config.toml) командой `supabase config push`. Это единственная настройка, которая делается не SQL-ом.

**5. Создайте пользователей.** *Authentication → Users → Add user → Create new user*: email, пароль и галочка **Auto Confirm User**. Нужен минимум один постановщик и два исполнителя. Новый пользователь по умолчанию — **исполнитель** (минимум прав). Постановщиком его делает администратор базы в *SQL Editor*:

```sql
update public.profiles
set role = 'manager', full_name = 'Анна Воронцова'
where id = (select id from auth.users where email = 'manager@example.com');

-- имена исполнителей (иначе в интерфейсе будет часть email до «@»)
update public.profiles set full_name = 'Игорь Петров'
where id = (select id from auth.users where email = 'executor1@example.com');
```

*Быстрее:* `npm run demo-users` создаёт 2 постановщиков и 2 исполнителей. Скрипт генерирует случайные пароли, пишет SQL с **хэшами** в `supabase/demo-users.local.sql` (выполните его в *SQL Editor*), а сами пароли — в `ДОСТУПЫ.local.md`. Оба файла в `.gitignore`. Скрипт добавляет строки прямо в служебные таблицы `auth.users` и `auth.identities` (так же, как панель), поэтому штатный способ выше надёжнее при смене версии Supabase.

**6. Демо-данные (по желанию).** Выполните [`supabase/seed.sql`](supabase/seed.sql) в *SQL Editor*: 3 объекта, 10 задач во всех статусах с историей. Скрипт берёт первых созданных пользователей по ролям (нужен минимум 1 постановщик и 2 исполнителя) и безопасен при повторном запуске.

**7. Подключите приложение.** Скопируйте `.env.example` в `.env.local` и вставьте *Project URL* и *Publishable key* (*Project Settings → API Keys*):

```
VITE_SUPABASE_URL=https://<project-ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

Это **публичный** ключ: он по замыслу попадает в браузер, а доступ к данным ограничивают правила в базе. Секретный ключ (`service_role` / `sb_secret_…`) приложению не нужен и не используется; если подставить его по ошибке, приложение откажется запускаться.

**8. Запуск**

```bash
npm run dev      # http://localhost:5173
```

## Проверки

```bash
npm run test:db        # 99 тестов правил базы: «атаки» от имени гостя, исполнителя, постановщика
npm run test:live      # 31 проверка «чёрным ящиком» на ЖИВОМ проекте Supabase (после шагов 1–7)
npm run typecheck      # TypeScript
npm run lint           # ESLint
npm run build          # production-сборка
npm run check:secrets  # нет ли секретных ключей в репозитории и сборке (--history: и в истории git)
```

`test:db` не требует ни Docker, ни облака: Postgres поднимается в памяти ([PGlite](https://pglite.dev)), туда применяются миграции из репозитория, а запросы выполняются под ролями Supabase (`anon` / `authenticated` + JWT) — так же, как это делает API.

`test:live` проверяет то же самое на настоящем проекте: обычные HTTP-запросы к Auth и REST API с публичным ключом. Данные он не меняет (разрешённое — только чтение, запрещённое должно быть отклонено), пароли не выводит. Ему нужны `.env.local` и доступы постановщика и исполнителя: файл `ДОСТУПЫ.local.md` (его создаёт `npm run demo-users`) или переменные `LIVE_MANAGER_EMAIL`, `LIVE_MANAGER_PASSWORD`, `LIVE_EXECUTOR_EMAIL`, `LIVE_EXECUTOR_PASSWORD`; без них проверка пропускается. Если регистрация в проекте открыта (или включены анонимные входы), он честно упадёт на пункте «открытая регистрация и анонимные входы отключены». Подробности — в [docs/security.md](docs/security.md).

## Деплой (Vercel)

1. *Add New → Project* → импортируйте репозиторий. Framework — Vite (определится сам, см. [`vercel.json`](vercel.json)).
2. В *Environment Variables* добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` (только публичные значения).
3. *Deploy*. После этого в Supabase (*Authentication → URL Configuration*) укажите адрес сайта как **Site URL**.

Подойдёт и любой статический хостинг: сборка — папка `dist`, все пути должны отдавать `index.html`.

**Из командной строки** (так развёрнуто демо). Нужен Vercel CLI версии 65 и выше: старый вход по GitHub, GitLab и email отключён, поэтому сначала `npm i -g vercel@latest`. Дальше:

```bash
vercel login            # вход по ссылке и коду (Device Flow): подтвердите в браузере
vercel link --yes       # создаёт проект в вашем аккаунте
vercel env add VITE_SUPABASE_URL --environment production,preview --value <адрес проекта> --no-sensitive --yes
vercel env add VITE_SUPABASE_PUBLISHABLE_KEY --environment production,preview --value <публичный ключ> --no-sensitive --yes
vercel deploy --prod --yes
```

Файл [`.vercelignore`](.vercelignore) не даёт загрузить в Vercel локальные заметки, тесты и миграции. Проверяющим давайте адрес вида `<проект>.vercel.app`: он открыт без входа, а адрес конкретного деплоя (`…-<хэш>-<аккаунт>.vercel.app`) закрыт защитой Vercel. Автодеплой по `git push` включается в *Settings → Git* проекта (приложению Vercel нужен доступ к репозиторию на GitHub); пока деплой делается вручную.

## Структура

```
supabase/
  migrations/   схема, помощники и профили, права доступа (RLS), жизненный цикл задачи и журнал
  seed.sql      демо-данные (без паролей и ключей)
  config.toml   настройки Supabase CLI (регистрация выключена)
tests/db/       тесты правил базы на Postgres в памяти
tests/live/     проверка защиты на живом проекте «чёрным ящиком» (npm run test:live)
scripts/        check-secrets (поиск секретов), demo-users (демо-пользователи со случайными паролями)
src/
  api/          запросы к Supabase (TanStack Query)
  auth/         вход, сессия, защита маршрутов
  components/   интерфейс: формы, таблица задач, действия, история
  pages/        экраны
  lib/          конфигурация, типы, подписи статусов, общая логика переходов
docs/           объяснение для руководителя, решения и допущения, безопасность
```

## Как это защищено — коротко

* **RLS на всех таблицах**, права гостя (`anon`) сняты полностью, у вошедших — минимум по таблицам и колонкам.
* **Исполнитель** физически получает из базы только свои задачи и связанные объекты; чужое — «не найдено».
* **Статус меняется только функцией `change_task_status()`**, которая проверяет роль, назначение, допустимость перехода по таблице `task_transitions` и обязательный комментарий. Три независимых замка: нет права записи в колонку `status`, триггер-страж, проверки функции.
* **Журнал только дописывается:** нет прав на запись через API, а триггер запрещает менять и удалять записи даже владельцу базы.
* **Регистрация закрыта**; роль можно задать только администратору (`app_metadata`), а не самому пользователю.
* **Секретов нет** ни во фронтенде, ни в репозитории: `.env*` в `.gitignore`, в браузер уходит только публичный ключ.
