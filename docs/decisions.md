# Решения и допущения

Здесь — что я решил сам там, где ТЗ допускает разные трактовки, что добавил сверх ТЗ и чего не сделал.

## Где ТЗ неоднозначно и что я выбрал

1. **Кто принимает задачу.** В ТЗ указана роль («постановщик»), а не автор. Принять или вернуть на доработку может **любой** постановщик, не только создавший задачу: при нескольких руководителях так проще. Ограничение «только автор» — одна строка в функции `change_task_status`.
2. **Исполнитель обязателен.** «Неназначенных» задач нет — у каждой всегда есть ответственный. Исполнителем можно назначить только пользователя с ролью «Исполнитель» (проверяет триггер), так что постановщик не может поставить задачу на самого себя.
3. **Переназначение и перенос.** Постановщик может в любой момент сменить исполнителя или объект задачи. Статус при этом не сбрасывается, а прежний исполнитель сразу теряет доступ к задаче и её истории. Смена исполнителя в журнал не пишется: по ТЗ в журнале — смены **статуса** (см. «Не сделано»).
4. **Создание задачи — первая запись журнала** («— → Новая», автор — постановщик): в таблице переходов ТЗ это отдельная строка.
5. **Комментарий** обязателен только при возврате на доработку. При остальных переходах его можно добавить по желанию, он сохранится в истории. Комментарий из одних пробелов, табов и переводов строк считается пустым (эту ошибку нашёл тест: стандартная обрезка пробелов в Postgres не убирает переводы строк).
6. **Удаление.** Задача удаляется физически, объект — вместе со всеми своими задачами; интерфейс просит подтверждение и называет, сколько задач пропадёт. **Журнал статусов остаётся в базе**: я намеренно не делал внешний ключ журнала на задачу, чтобы удаление не стирало историю («историю нельзя удалить»). Исполнителю и интерфейсу она недоступна. Альтернатива — «мягкое» удаление с пометкой; не делал, чтобы не усложнять модель.
7. **Что видит исполнитель.** Свои задачи; объекты, где у него есть задачи; в карточке объекта — только свои задачи. Из профилей — себя и постановщиков (нужны, чтобы показать автора задачи), других исполнителей — нет: наружу уходит меньше персональных данных, чем допускает ТЗ.
8. **Роли и регистрация.** Роль хранится в `profiles.role`, клиентам запись туда закрыта. Пользователя создаёт администратор в панели Supabase; по умолчанию он «исполнитель» — минимум прав. Постановщиком его делает администратор (SQL или `app_metadata.role = 'manager'` при создании). Роль **не** читается из `user_metadata`: это поле пользователь может править сам.
9. **Удаление пользователей.** Пользователя, у которого есть задачи, удалить нельзя (запрет в базе): задачи сначала передают другому. Имя в журнале хранится «снимком» на момент действия — переименование или удаление пользователя историю не портит.
10. **Статус меняется только функцией.** Вместо обычной записи в поле `status` — вызов `change_task_status(задача, новый статус, комментарий)`: комментарий приходит вместе с переходом и попадает в журнал в той же транзакции. Прямая запись в `status` закрыта (право на колонку + триггер-страж).
11. **Правила переходов — в таблице** `task_transitions`, а не «зашиты» в код. Матрицу из ТЗ можно прочитать глазами; её же читает интерфейс, чтобы показывать только доступные кнопки. Решение о допуске всегда принимает база.

## Сверх ТЗ

- Экран **«Все задачи»** для постановщика с фильтром по статусу — удобная очередь проверки; сортировка «что требует внимания».
- **Автотесты безопасности** (`npm run test:db`): «атаки» на Postgres в памяти, включая полную матрицу «25 пар статусов × 3 вида пользователей».
- **Проверка на живом проекте** (`npm run test:live`): 31 запрос «чёрным ящиком» к настоящему API с публичным ключом, без изменения данных.
- **Защита от секретного ключа во фронтенде:** приложение не запустится, если в переменную с публичным ключом подставили `service_role` / `sb_secret_…`. Отдельная команда `npm run check:secrets` ищет секреты в репозитории, сборке и истории git.
- **Демо-пользователи без паролей в репозитории:** `npm run demo-users` генерирует случайные пароли, в SQL кладёт только их хэши, а сами пароли пишет в локальный файл вне git.
- Служебные функции вынесены в схему `private`, которая не публикуется через API.

## Не сделано / не успел

- Журнал правок полей задачи (название, описание, исполнитель) и аудит удалений.
- Деактивация пользователей и экран управления ими (по ТЗ пользователей создают вручную в Supabase).
- Пагинация, поиск, фильтры по объектам и исполнителям; уведомления; вложения и фото к задачам.
- E2E-тесты интерфейса (Playwright): интерфейс проверен вручную, а правила доступа — автотестами на уровне базы.
- Заголовок CSP, CAPTCHA и лимиты входа сверх встроенных в Supabase, двухфакторная защита.
- Если пользователю с задачами меняют роль на постановщика, его задачи нужно сначала передать: проверки при смене роли нет.

## Ограничения, о которых стоит знать

- Тесты базы идут на PGlite: он воспроизводит роли и права Supabase, но не слои PostgREST и GoTrue. Поэтому те же сценарии повторены на живом проекте (`npm run test:live`) и вручную в интерфейсе; результаты — в `docs/security.md`.
- Скрипт `demo-users` вставляет пользователей напрямую в служебные таблицы `auth.users` и `auth.identities`. Для демо это удобно, но при смене версии Supabase формат этих таблиц может измениться; штатный способ — панель Supabase (README, шаг 5).
- Служебный ключ `service_role` по замыслу Supabase обходит RLS и хранится только у администратора. Триггеры (неизменяемый журнал, страж статуса) действуют и для него, но владелец базы технически может их отключить — от владельца защиты нет нигде.
- Отключение регистрации — настройка проекта Supabase (панель или `supabase config push`), SQL её не меняет. Если её случайно включить, «самозванец» получит роль исполнителя без задач и не увидит ничего.

## Технические выборы

- **TypeScript 5.9, а не 7:** `typescript-eslint` пока не поддерживает 7-ю версию. **Mantine 8:** проверенная версия; 9-я требует более свежего React.
- **TanStack Query** — кэш и обновление данных; при выходе и смене пользователя кэш очищается, чтобы данные одного пользователя не «просочились» к другому.
- **Mantine** — готовые доступные компоненты; дизайн по условию не оценивается, поэтому минимальный.
