# Безопасность: требования ТЗ → как выполнено → чем проверено

Принцип: **решает база, а не интерфейс.** Интерфейс прячет лишние кнопки для удобства, но все правила проверяются там, где данные лежат, поэтому обращение к Supabase напрямую (curl, Postman, консоль браузера) ничего не обходит.

## Слои защиты

1. **Границы API.** Роль `anon` (гость без входа) не имеет прав ни на одну таблицу. Роль `authenticated` получает только необходимый минимум: `GRANT` выдан по таблицам и даже по **колонкам** (например, в `tasks` писать можно только `title`, `description`, `object_id`, `executor_id`; в `status`, `author_id`, `created_at` — нельзя).
2. **RLS (политики строк)** включён на всех пяти таблицах: какие именно строки видит и меняет каждый пользователь.
3. **Функция `change_task_status()` + триггеры:** единственный способ сменить статус; журнал дописывается только изнутри базы и защищён от изменения.
4. **Схема `private`:** служебные функции (`is_manager()`, триггеры) лежат в схеме, которую Supabase не публикует наружу.

## Требования ТЗ

| № | Требование | Как выполнено | Чем проверено |
| --- | --- | --- | --- |
| 1 | Права закрыты на уровне базы (RLS) | RLS на всех таблицах; права `anon` сняты; у `authenticated` — минимум по таблицам и колонкам (миграция 3) | группы «Гость», «Исполнитель: чего он не может», «Постановщик» |
| 2 | Исполнитель не читает и не меняет чужие задачи | Политика `tasks_select`: `executor_id = auth.uid()`; объекты видны только при наличии своей задачи; изменение и удаление — только постановщику; чужая задача для `change_task_status` — «не найдена» | «Исполнитель: что он видит» (в т. ч. чтение по прямому адресу), «чего он не может» (изменяется и удаляется 0 строк) |
| 3 | Переходы проверяются на стороне базы | `change_task_status()` сверяет переход с таблицей `task_transitions`, роль, назначение и обязательный комментарий; прямая запись в `status` закрыта правом на колонку **и** триггером-стражем | «Переходы статусов»: все 25 пар × 3 вида пользователей; «Постановщик»: возврат без комментария (в т. ч. из одних переводов строк) невозможен |
| 4 | Историю нельзя подделать, изменить, удалить через API | Нет прав `INSERT/UPDATE/DELETE` для API и нет политик на запись; запись делают только триггер создания и функция смены статуса; триггер запрещает менять и удалять строки даже владельцу базы | «Исполнитель: чего он не может», «Постановщик», «Журнал статусов» |
| 5 | Открытая регистрация отключена | Настройка Supabase Auth (`enable_signup = false`, см. `supabase/config.toml` и README, шаг 4). Запасной заслон в базе: роль берётся только из `app_metadata` (её пишет администратор), а «самозванец» без задач ничего не видит | «Профили и роли»; на живом проекте — `test:live` читает `/auth/v1/settings` и пробует самостоятельную регистрацию |
| 6 | Секретные ключи не попадают во фронтенд и репозиторий | В браузер уходит только публичный ключ; `service_role` нигде не используется; `.env*` в `.gitignore`; приложение отказывается стартовать с секретным ключом (`src/lib/config.ts`) | `npm run check:secrets` — сканирует репозиторий, сборку `dist` и (с `--history`) всю историю git |

## Что кому разрешено

| Объект | Гость | Исполнитель | Постановщик |
| --- | --- | --- | --- |
| `profiles` | — | читает себя и постановщиков | читает всех |
| `objects` | — | читает объекты, где у него есть задачи | читает все; создаёт, меняет (`name`, `address`), удаляет |
| `tasks` | — | читает только свои | читает все; создаёт, меняет (`title`, `description`, `object_id`, `executor_id`), удаляет |
| `task_status_history` | — | читает журнал своих задач | читает весь; **писать не может никто** |
| `task_transitions` | — | читает | читает |
| `change_task_status()` | — | свои задачи, переходы «исполнителя» | любые задачи, переходы «постановщика» |

## Как проверить руками

Автоматически: `npm run test:live` (см. README). Или вручную: любой проверяющий может повторить «атаки» на живом проекте. Подставьте адрес проекта и публичный ключ (bash / Git Bash):

```bash
URL="https://<project-ref>.supabase.co"; KEY="<publishable key>"

# 1. Войти исполнителем и получить токен
TOKEN=$(curl -s "$URL/auth/v1/token?grant_type=password" -H "apikey: $KEY" -H "Content-Type: application/json" \
  -d '{"email":"<email исполнителя>","password":"<пароль>"}' | sed -E 's/.*"access_token":"([^"]+)".*/\1/')

# 2. Прочитать задачи: придут только назначенные на этого исполнителя
curl -s "$URL/rest/v1/tasks?select=id,title,status" -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN"

# 3. Поменять статус напрямую, минуя функцию: отказ (permission denied)
curl -s -X PATCH "$URL/rest/v1/tasks?id=eq.<id своей задачи>" -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"status":"accepted"}'

# 4. Запрещённый переход через функцию (из «Новая» сразу «На проверке»): ошибка с пояснением
curl -s -X POST "$URL/rest/v1/rpc/change_task_status" -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"p_task_id":"<id своей задачи>","p_new_status":"in_review"}'

# 5. Записать в журнал: отказ
curl -s -X POST "$URL/rest/v1/task_status_history" -H "apikey: $KEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"task_id":"<id>","to_status":"accepted","actor_id":"<id>","actor_name":"x"}'

# 6. Зарегистрироваться самому: отказ («Signups not allowed»)
curl -s -X POST "$URL/auth/v1/signup" -H "apikey: $KEY" -H "Content-Type: application/json" \
  -d '{"email":"intruder@example.com","password":"Str0ngPassw0rd!"}'
```

Секреты в репозитории и сборке (скрипт ищет настоящие ключи: `sb_secret_…`, JWT с ролью `service_role`, строки подключения к базе с паролем; публичный ключ секретом не считает):

```bash
npm run build
npm run check:secrets                        # рабочая папка и dist
node scripts/check-secrets.mjs --history     # плюс вся история git
```

## Автотесты (`npm run test:db`)

Миграции применяются к Postgres в памяти (PGlite), а запросы выполняются под ролями Supabase (`anon` / `authenticated` + JWT в настройках сессии) — так же, как их выполняет API. Покрыто:

- **Гость:** не читает и не пишет ни одну таблицу, не вызывает функцию смены статуса, не видит служебную схему.
- **Исполнитель, чтение:** только свои задачи, объекты со своими задачами, журнал своих задач; профили — себя и постановщиков; чужая задача по прямому `id` не отдаётся.
- **Исполнитель, запись:** не создаёт, не меняет и не удаляет объекты и задачи (изменяется 0 строк); не меняет статус напрямую (даже подделав «пропуск» для триггера); не пишет, не правит и не удаляет журнал; не повышает себя до постановщика; не правит правила переходов; не вызывает служебные функции.
- **Матрица переходов:** для каждой из 25 пар «из → в» проверены назначенный исполнитель, чужой исполнитель и постановщик — разрешено ровно то, что в ТЗ.
- **Постановщик:** создаёт, меняет, удаляет; не создаёт задачу в чужом статусе, с чужим автором, с «пустым» названием; не назначает исполнителем постановщика; не меняет статус напрямую; не пишет в журнал; любой постановщик может принять задачу.
- **Журнал:** полный путь задачи (кто, из какого в какой, комментарий без лишних пробелов); неизменяем даже для владельца базы; при удалении задачи остаётся в базе, но исполнителю недоступен.
- **Профили:** роль только из `app_metadata`; из `user_metadata` игнорируется; пользователя с задачами удалить нельзя.
- **Целостность:** статус каждой задачи равен последней записи её журнала; в журнале только создание и разрешённые переходы; у каждой задачи ровно одна запись о создании.
- **Демо-данные:** `seed.sql` даёт согласованные данные, не дублируется при повторном запуске.

## Проверено на живом проекте

Те же сценарии повторены на настоящем Supabase (PostgREST + GoTrue), а не только на Postgres в памяти: проект `crm-objects-tasks`, регион eu-central-1, 7 ноября 2026.

**Автоматически — `npm run test:live`:** 31 проверка «чёрным ящиком» (HTTP-запросы с публичным ключом, как у любого постороннего клиента; данные не меняются, в конце проверяется, что они остались прежними). Результат: **31 из 31 пройдено** (8 ноября 2026, после того как в панели выключен переключатель «Allow new users to sign up» — единственная настройка, которую нельзя сделать SQL-ом; README, шаг 4). Проверено на живой базе:

- гость не читает ни одну из 5 таблиц, не создаёт объекты, не вызывает функцию смены статуса — везде отказ `42501`;
- исполнитель получает только свои задачи (в выдаче нет ни одной чужой), только объекты со своими задачами, журнал только своих задач; профили — себя и постановщиков, других исполнителей нет; чужая задача по прямому `id` не отдаётся;
- прямая запись в `status` — отказ `permission denied`; правка и удаление своих и чужих задач — 0 строк; создание объектов и задач, запись, правка и удаление журнала, повышение себя до постановщика, правка правил переходов — отказ;
- функция смены статуса: чужая задача — «не найдена»; запрещённые переходы — «запрещён»; принять свою работу исполнитель не может;
- постановщик: не меняет статус напрямую, не создаёт задачу сразу в другом статусе, не пишет в журнал, не выполняет переходы исполнителя; возврат на доработку без комментария (в том числе из одних пробелов и переводов строк) отклоняется;
- вход демо-пользователей, созданных скриптом `demo-users`, работает; неверный пароль отклоняется (`invalid_credentials`);
- регистрация закрыта: в настройках проекта `disable_signup = true`, анонимные входы выключены, включён только вход по email; реальная попытка самостоятельной регистрации отклоняется с кодом `signup_disabled`, и пользователь при этом не создаётся.

**Вручную в интерфейсе** (приложение, подключённое к тому же проекту): вход обеими ролями; исполнитель видит один объект из четырёх и только свою задачу, чужая задача и чужой объект по прямому адресу дают «не найдена», адрес `/tasks` (только для постановщика) перенаправляет на «Мои задачи»; полный цикл задачи: создание постановщиком → «Взять в работу» → «Отправить на проверку» → «Вернуть на доработку» с комментарием → «Принять»; создание, редактирование и удаление объектов и задач; при удалении объекта его задачи удаляются каскадом, а журнал остаётся в базе.

**Штатные проверки Supabase (advisors):**

- *Безопасность* — одно предупреждение `authenticated_security_definer_function_executable` для `public.change_task_status`. Оно **осознанное**: функция — единственная «дверь» смены статуса, она выполняется с правами владельца и сама проверяет, кто вызывает. Других замечаний (RLS, изменяемый `search_path`, доступ гостя) нет.
- *Производительность* — только информационное «неиспользуемые индексы» на пустой базе без трафика; непроиндексированных внешних ключей и проблем с RLS нет.

## Что защита не закрывает

- **Администратор проекта всемогущ.** Ключ `service_role` обходит RLS по замыслу Supabase. Он не используется в приложении и не лежит в репозитории, но его утечка равна утечке всей базы. Если он где-то засветился — перевыпустить немедленно.
- **Владелец базы может отключить триггеры.** От владельца не защищает ни одна схема доступа.
- **Нет журнала правок полей задачи** (название, описание, исполнитель) — только журнал статусов, как в ТЗ.
- **Нет дополнительных лимитов и CAPTCHA** на вход, только встроенные в Supabase Auth; нет двухфакторной защиты.
